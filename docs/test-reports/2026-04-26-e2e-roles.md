## P1 Bugs (critical — block primary workflows)

### B1. `PATCH /v1/leads/:id` always returns 400 "Validation failed" (FIXED IN-PLACE)

**Where:** `apps/api/src/modules/leads/leads.controller.ts:58`
**Severity:** P1 — blocks every dealer status transition, every owner-side observation of progress, every close-deal path
**Root cause:** Method-level `@UsePipes(new ZodValidationPipe(updateLeadSchema))` runs the schema on _every_ parameter — including the `:id` path param. The UUID string can't match an object schema, so Zod's `safeParse` fails first.
**Fix applied (inline, to unblock W2/W4/M1/M3):** Moved the pipe to the body decorator: `@Body(new ZodValidationPipe(updateLeadSchema)) body`. Confirmed working — full status walk NEW → CONTACTED → VISIT_SCHEDULED → VISITED → NEGOTIATING → CLOSED now returns 200 each.
**Action:** No further work; commit and add a regression test (suggest: integration test that asserts `PATCH /leads/:id` accepts `{status:"CONTACTED"}` and returns 200).
**Repro (before fix):** `curl -X PATCH /v1/leads/<id> -d '{"status":"CONTACTED"}'` → `400 Validation failed`.

### B2. RWA admin sees dealers from _every_ society (society-scope leak)

**Where:** `apps/api/src/modules/dealers/dealers.service.ts findAll` (suspected — society scoping not enforced)
**Severity:** P1 — privacy / governance violation; an RWA admin in Green Valley should never see a dealer roster from Sunrise Towers
**Repro:** Login as `+919999900002` (Green Valley RWA admin). `GET /v1/dealers` returns 3 dealers including "Sunrise Dealer" (society = Sunrise Towers).
**Expected:** Returned dealers filtered to `society_id IN (SELECT id FROM societies WHERE rwa_admin_id = <currentUserId>)`.
**Action:** Read `dealers.service.ts findAll`; add `where.societyId` based on the requesting user's role. SUPER_ADMIN sees all; RWA_ADMIN scoped; DEALER sees only their own dealer record.

### B3. Unverified properties surface in public `/v1/search/properties`

**Where:** `apps/api/src/modules/search/search.service.ts` (filter on `verificationStatus` missing)
**Severity:** P1 — content moderation bypass. Per CLAUDE.md, only RWA-approved listings should be discoverable to buyers; here a freshly created property (`verificationStatus = PENDING`) is immediately searchable and enquirable.
**Repro:** As OWNER, `POST /v1/properties` with valid body. Without any verification step, `GET /v1/search/properties` includes the new property in results.
**Expected:** Search returns only properties with `verificationStatus IN ('RWA_APPROVED', 'VERIFIED')` for unauthenticated callers (and SUPER_ADMIN sees all).
**Action:** Add the filter clause in `SearchService.queryProperties`. Decide whether RWA_APPROVED alone is enough or if `VERIFIED` (the SA-final-approval state) is required for the public search.

## P2 Bugs (works but degraded / inconsistent)

### B4. SUPER_ADMIN cannot call `PATCH /leads/:id/approve-visit` despite `@Roles('OWNER','SUPER_ADMIN')`

**Where:** `apps/api/src/modules/leads/leads.service.ts approveVisit` line ~189
**Severity:** P2 — guard says SA is allowed; service-layer ownership check then refuses with 400 "Only the property owner can approve visits". Guard intent and service intent disagree.
**Action:** In `approveVisit`, allow override when caller's role is SUPER_ADMIN: skip the `lead.property.ownerId !== ownerId` check for SA. Or, if SA shouldn't actually have this power, remove `'SUPER_ADMIN'` from `@Roles()`.

### B5. `PATCH /dealers/:id/kyc` accepts garbage and silently REJECTS the dealer

**Where:** `apps/api/src/modules/dealers/dealers.controller.ts:62-70`
**Severity:** P2 — destructive default; an SA who sends `{kycStatus:"APPROVED"}` (the field name used in EVERY other endpoint) ends up _rejecting_ the dealer because the controller expects `body.status` and the service ternary defaults missing input to `'REJECTED'`.
**Repro:** `PATCH /v1/dealers/<id>/kyc -d '{"kycStatus":"APPROVED"}'` → 200, but DB shows `kyc_status = KYC_REJECTED`.
**Action:** Two fixes (do both):

1. Validate request body with a Zod schema that requires `status: 'APPROVED' | 'REJECTED'`. Reject anything else with 400.
2. Rename to `kycStatus` for consistency, OR alias both keys for backwards-compat.

## P3 Polish

### B6. `VISIT_SCHEDULED` accepts no `visitDate`

Lead status update lets you set `status: VISIT_SCHEDULED` without a `visitDate`. Logical: scheduled visits should require a date. Add a Zod refinement to the update schema: `if status === 'VISIT_SCHEDULED' then visitDate is required`.

### B7. `POST /communication/conversations` returns 500 on missing `participantId`

The endpoint is unvalidated. Missing `participantId` → Prisma JSONB query fails with `Invalid value for argument array_contains[1]: undefined`. Add Zod validation; reject with 400 + actionable message. Bonus: the API could auto-derive the other participant from the lead's `buyerId`/`dealerId` when the caller is one of them.

## Missing Entirely (no UI, no API)

### B8. No way to assign an RWA admin to a society

The `societies.rwa_admin_id` column exists, the data model expects it, but `updateSocietySchema` omits the field, so `PATCH /societies/:id` silently ignores it (verified — request 200s, value unchanged). And there's no dedicated "assign" endpoint.
**Action:** Either add `rwaAdminId: z.string().uuid().optional()` to `updateSocietySchema`, or create `POST /admin/societies/:id/assign-rwa { userId }` with a role-promotion side-effect (auto-set the user's role to RWA_ADMIN if they're not already).

### B9. SUPER_ADMIN is not notified on close-deal

Notification fanout on close-deal hits BUYER + OWNER + DEALER. SA oversees commissions and arguably should know. Low importance — easy to add a 4th `notify(superAdminId, ...)` call.
