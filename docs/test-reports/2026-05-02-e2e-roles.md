### B9 — `DEAL` notifications on lead close — **STILL OPEN, slightly regressed** ❌

- Test: trigger `PATCH /v1/leads/:id` with status walk → `CLOSED`. Then query `notifications` for any new rows.
- Observed: **Zero `DEAL` notifications created** for any role (Dealer, Buyer, Owner, or SA) during three separate close walks performed in this run. Most recent `DEAL` rows in DB are dated 2026-04-26 14:16:56 (previous test run).
- Root cause sketch: `LeadsService.update()` (`leads.service.ts:163-180`) just patches the status — it does not call `notificationsService` for any transition, including `CLOSED`. Notifications-on-close only fire from `closeDeal()` (`leads.service.ts:201`), which is reached via the separate `POST /v1/leads/:id/close-deal` endpoint that requires `dealValue`/`type`.
- Effect: Any test or UI that drives the lead to CLOSED via the generic status PATCH leaves the system in a half-closed state — `status=CLOSED` but no transaction row, no commission row, no notifications. SA-notification gap is a subset of this larger problem.
- Severity bumped to **P2 (was P3)** because the silent split-brain affects accounting, not just notification UX.
- Recommended fix: in `LeadsService.update`, when `data.status === 'CLOSED'`, refuse the patch with a 400 directing the caller to `POST /leads/:id/close-deal`. (Forcing the close-deal call ensures transaction + commission + notifications all fire.) Alternative: have `update()` emit notifications for status changes (LEAD_STATUS_CHANGED) and add SA as a recipient when status hits CLOSED.
